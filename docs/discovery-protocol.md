# 组播发现协议

本文描述节点通过 UDP 组播互相发现时使用的报文格式与流程。该通道只用于公告「我是谁、我的地址与数据端口是多少」，不承载会话信令和业务数据。

## 1. 约定

- 默认组播地址 `239.255.42.99`，默认端口 `45454`，均可通过 `DiscoveryConfig` 配置
- 组播 TTL 固定为 1，报文只在本网段传播
- 所有多字节字段使用网络字节序（大端）
- 报文固定 16 字节，无变长负载
- 报文携带发送方 IP，接收方优先使用报文中的地址

## 2. 报文格式

协议版本 `1`：

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 4 | `magic` | `0x4E50524F`，ASCII `NPRO` |
| 4 | 1 | `version` | 当前为 `1` |
| 5 | 1 | `type` | 1=Announce，2=Bye |
| 6 | 4 | `address` | 发送方可连接的 IPv4 地址，网络序 |
| 10 | 2 | `port` | 发送方数据端口（非组播端口） |
| 12 | 4 | `nodeId` | 发送方节点标识 |

字段说明：

- `address` 紧跟在 `type` 之后，是发送方声明的可连接地址，填 `0` 表示未知，接收方回退到 `recvfrom` 源地址
- `port` 是会话与数据传输使用的端口，与组播端口无关
- `nodeId` 放在最后，标识节点身份
- 多网卡机器应填入希望被连接的网卡地址，避免对端按源地址连到不可达的接口

报文固定 16 字节，解析时必须完整读取 `address` 字段，长度不足时直接丢弃。后续如果需要扩展字段，再提升 `version`。

## 3. 消息类型

| type | 名称 | 用途 | 频率 |
| --- | --- | --- | --- |
| 1 | Announce | 公告自身地址、端口与存在 | 每 `announceIntervalMs`（默认 3000ms） |
| 2 | Bye | 主动通知即将离开 | 停止前发送一次 |

`Bye` 是可选的优化：不发送也可以，对端依靠 `peerTimeoutMs`（默认 10000ms）超时淘汰。

## 4. 校验规则

接收方按顺序校验，任一步失败直接丢弃：

1. 报文长度 ≥ 16
2. `magic` 正确
3. `version` 为 1
4. `type` 为 1 或 2
5. `port != 0`

额外过滤：

- `nodeId` 等于自身节点标识的报文丢弃（组播回环会收到自己的包）
- `address` 若既不等于 0 也不等于源地址，记录一条 Debug 日志，仍以报文地址为准

## 5. 地址选择

```
解析报文 address
  ├─ 非 0 且为合法 IPv4 → 使用报文地址
  ├─ 为 0               → 使用 recvfrom 源地址
  └─ 非法               → 使用 recvfrom 源地址
```

为什么仍然保留源地址回退：

- 发送方可能不知道自己的出口地址，填 0
- 填写的地址可能非法或属于不可路由网段
- 源地址天然是本次组播的出口地址，多数场景与报文地址一致

报文地址与源地址不一致的典型原因：发送方主动指定了某块业务网卡，而组播从默认路由网卡发出。此时应以报文地址为准，因为那是发送方希望被连接的地址。

## 6. 发现流程

```
节点 A 启动
  ├─ 创建数据 socket，绑定数据端口（0 则系统分配）
  ├─ 创建发现 socket，绑定组播端口并加入组播组
  ├─ 设置组播 TTL 1、开启回环
  └─ 开始周期 Announce（携带 nodeId、数据端口、本机地址）

节点 B 启动后收到 A 的 Announce
  ├─ 校验报文
  ├─ 选择地址（报文地址优先，源地址回退）
  ├─ 用地址 + port + nodeId 构造 PeerInfo
  └─ 写入 PeerTable，回调上层

A 超过 peerTimeoutMs 没有新公告
  └─ B 从 PeerTable 淘汰 A
```

`Announce` 必须在数据 socket 就绪之后才发送，保证对端拿到端口时可以直接建立会话。

## 7. 报文示例

Announce：`nodeId = 0x0000000A`，`port = 7001`（`0x1B59`），`address = 192.168.1.20`（`0xC0A80114`）

```
4E 50 52 4F  01  01  C0 A8 01 14  1B 59  00 00 00 0A
```

Bye：同一节点，`type = 2`

```
4E 50 52 4F  01  02  C0 A8 01 14  1B 59  00 00 00 0A
```

## 8. 与组播配置相关的行为

| 配置 | 未配置时 | 影响 |
| --- | --- | --- |
| `multicastGroup` | `239.255.42.99` | 组不同则互相不可见 |
| `multicastPort` | `45454` | 端口不同则互相不可见 |
| `announceIntervalMs` | 3000 | 越小发现越快，组播流量越大 |
| `peerTimeoutMs` | 10000 | 越小淘汰越快，误判概率越高 |

同一局域网内所有节点必须使用相同的组播组与端口才能互相发现。

## 9. 与会话协议的对比

| 项 | 发现协议 | 会话协议 |
| --- | --- | --- |
| magic | `NPRO` | `NPSN` |
| 传输 | UDP 组播 `239.255.42.99:45454` | UDP 单播，节点数据端口 |
| 长度 | 固定 16 字节 | 12 ~ 24 字节（信令），24 字节以上（数据） |
| 主要字段 | `nodeId`、`port`、`address` | `sessionId`、`nodeId`、`nonce` |
| 方向 | 一对多 | 点对点 |
| 职责 | 告知可达地址 | 建立 / 关闭会话、传输数据 |

两个协议使用不同端口和不同 magic，互不干扰；在数据 socket 上收到 `NPRO` 报文按异常丢弃，在组播 socket 上收到 `NPSN` 报文同理。

## 10. 网络与安全边界

- 组播可能被交换机或虚拟化平台过滤，跨网段不可用（TTL 1 也是这个目的）
- 无认证，局域网内任何主机都能伪造 `nodeId`、`port` 和 `address`
- 伪造 `address` 会让对端向该地址发起会话，属于可信网络内的已知风险
- 仅支持 IPv4 组播，IPv6 组播未实现
- 报文没有序号，乱序或重复公告不会造成状态错误（写入节点表是幂等的）

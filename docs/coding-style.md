# 代码风格与注释规范

本文规定注释的写法与覆盖范围。目标是让读代码的人在不运行程序的前提下，能判断**谁调用、谁拥有、何时失效、返回值代表什么**。

## 1. 注释分层

不同位置承担不同职责，**不重复**是硬要求：

| 位置 | 要求 | 写什么 |
| --- | --- | --- |
| `include/` 公共头 | 必须完整 | 类/结构说明、每个 public 函数的说明 + `@param` + `@return`、每个成员变量说明 |
| `src/**/*.h` 内部头 | 必须完整 | 同上；私有函数至少一行说明职责 |
| `src/**/*.cpp` 实现 | 只写「为什么」 | 顺序约束、锁边界、历史兼容、非显然的取舍；**不重复头文件里的参数说明** |
| 测试 | 用例名即注释 | 用例名用中文描述行为；构造复杂输入时加一行说明意图 |
| 文档 | 与代码同一次提交 | 行为、接口、命名变化必须同步文档 |

判断标准：如果删掉这行注释，读者仍然能从代码本身看出「做了什么」，那这行注释就不该存在；如果看不出「为什么这样做」，就必须写。

豁免：以下样板不要求逐个注释，但同类应保持统一写法（要么都注释，要么都留白）：

- 拷贝/移动构造与赋值运算符的 `= delete`；
- `= default` 的默认构造；
- 一组同构的模板转发方法（如 `Log::debug` / `info` / `warning` / `error`）可以只写分组说明。

## 2. 函数注释：说明 + 参数 + 返回值

每个 `public` / `protected` 函数必须写完整块注释，三部分缺一不可：

1. **函数说明**：一句话讲清做什么；有前置条件、状态变化或副作用时另起一段。
2. **`@param`**：按声明顺序，逐个说明**语义**（不是复述类型）；输出参数必须写明何时被写入。
3. **`@return`**：非 `void` 函数必须写；区分「已受理」「已送达」「成功/失败」三类语义。

```cpp
/**
 * 提交一帧，走可靠有序通道。
 *
 * 状态不是 Connected 时直接拒绝，不会排队。
 *
 * @param frame 已填好 type / streamId / payload 的帧。
 * @return 已受理返回 true；连接不可用或负载超限返回 false。
 * @note 返回 true 只表示本地受理，不代表对端收到；窗口不足时内部排队。
 */
bool send(protocol::PeerFrame frame);
```

细则：

- 无参数、无返回值的函数也要有说明，可写成单行块注释：`/** 关闭连接并通知流层。 */`。
- `@param` 不得只写「见名知意」；指针/引用参数要写明所有权与失效时机（如「回调返回后失效」）。
- 返回 `bool` 时必须写清 true/false 各代表什么；返回 `0` 表示失败时写明「0 表示……」。
- 有线程约束、锁要求、回调时机时，用 `@note` 或说明段表达，不要埋在实现里。
- 私有函数不要求 `@param`，但必须有一行 `//` 说明职责；签名不自明时补充参数语义。

## 3. 成员变量：逐个说明作用

类与结构体的每个成员变量都必须有说明，写在行尾或上一行：

```cpp
private:
    std::uint32_t peerNodeId_ = 0;            // 对端节点标识
    std::uint32_t sendNext_ = 0;              // 下一个待分配序号
    std::deque<PendingFrame> sendQueue_;      // 已分配序号、等待确认的帧
    mutable std::mutex mutex_;                // 保护 streams_ 与 pending_
    std::atomic<bool> connected_{false};      // 供应用线程查询，避免读连接层状态
```

细则：

- 说明**用途与不变量**，不是复述类型（`uint32_t peerNodeId_` 不需要再写「是 uint32」）。
- 需要标明生命周期的成员写清「谁创建、何时失效」。
- 同一目的的成员可以加分组注释，但组内每行仍要有说明。
- 结构体字段同样适用；协议字段建议同时标注对应偏移或取值范围。

## 4. 通用格式

- 契约类注释用 `/** ... */`，实现说明用 `//`。
- 注释语言为中文，使用中文标点；代码标识符、类型名保持原样。
- 运行期输出用英文：`Log::*` 消息、`std::exception::what()` 文本、`static_assert` 诊断与 CMake `FATAL_ERROR` 消息一律英文，避免非 UTF-8 终端与构建日志乱码；格式为「子模块 动作 failed: 原因」，如 `data channel open failed: cannot bind 0.0.0.0:0`。
- 行宽以仓库根 `.clang-format` 的 `ColumnLimit: 120` 为准；提交前执行 `clang-format -i <file>`，并用 `clang-format --dry-run --Werror <file>` 复查。
- 类注释写职责、线程模型、生命周期；不写实现步骤。

## 5. 必须写注释的场景

| 场景 | 例子 |
| --- | --- |
| 线程边界 | 「只允许在业务线程调用」「任意线程可调用，内部加锁」 |
| 生命周期与所有权 | 「回调返回后 data 失效」「派生对象必须比使用者活得久」 |
| 锁与回调顺序 | 「持锁期间不得调用外部回调，否则应用重入会自锁」 |
| 返回值语义 | 「返回 true 表示已入队，不表示对端收到」 |
| 非显然的协议规则 | 「Ping 同时承担纯 ACK，因此不占交付序号」 |
| 历史与兼容约束 | 「与拆分前的 manager 行为保持一致」 |
| 边界条件 | 「size 为 0 视为非法」「超过 maxStreams 回 Reject」 |

## 6. 禁止的注释

- **复述代码**：`i++; // 自增 i`。
- **注释掉的代码**：删掉或提交到分支，不留注释块。
- **过时注释**：改了行为不同步注释，比没有注释更糟；PR 自检必须检查。
- **在头文件写实现细节**：头文件只描述契约，实现顺序与临时变量放在 `.cpp`。
- **无意义的 TODO**：必须带责任人或 issue，例如 `// TODO(#42): 支持流级窗口`。

## 7. 命名与注释一致

注释中的术语必须与 `docs/architecture.md` 的「1.1 术语」一致：

- Node = 网络实体（含本机），Peer = 对端；
- `nodeId` 指任意节点标识，`peerNodeId` 指对端，`localNodeId` 指本机；
- 不要在同一段注释里混用「节点」与「对端」指同一个对象。

## 8. 示例：同一段代码的两种写法

不合格：

```cpp
// 处理数据
void StreamMux::handleData(const protocol::PeerFrame& frame) {
    // 加锁
    std::lock_guard<std::mutex> lock(mutex_);
    // 查找
    auto it = streams_.find(frame.streamId);
    ...
}
```

合格：

```cpp
// 锁内只取回调并复制负载；回调必须出锁后执行，避免应用在 DataHandler 里
// 重入 sendData 时二次加锁造成自锁。
void StreamMux::handleData(const protocol::PeerFrame& frame) {
    const std::string payload = frame.payload;
    DataHandler handler;
    {
        std::lock_guard<std::mutex> lock(mutex_);
        ...
    }
    ...
}
```

## 9. 提交前自检

- [ ] 新增或修改的 public 函数有「说明 + @param + @return」完整注释。
- [ ] 新增的成员变量有说明（行尾或上一行）。
- [ ] 返回值、回调时机、线程约束已写明。
- [ ] 改动行为后，相关注释与文档已同步。
- [ ] 没有注释掉的代码与无主 TODO。
- [ ] 注释中的术语符合 Node / Peer 定义。
- [ ] `clang-format --dry-run --Werror` 对改动的文件通过。
